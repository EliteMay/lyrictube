# LyricTube 認証セキュリティ更新・本番反映ゲート（2026-10-22）

> **現状：PR内でコードとSQL・単体/隔離DBテストを用意した段階。Supabase本番へ未適用。**
> GitHub Pages上の既存データとログインを守るため、本文を満たすまで本番デプロイしない。

## 変更範囲

- 新規パスワードのみ、8〜128文字かつUTF-8最大72バイトで検査する。旧アカウントのログイン入力は変更しない。
- 重要なアカウント操作（パスワード変更・他アカウント削除）では、現在ログイン中アカウントのパスワードで再認証する。
- サーバーのJSON最大4MiB。これを超える同期リクエストは413として明示的に拒否するため、大きいライブラリで現実の保存/同期テストが必要。
- 重要なRPCは匿名・通常認証ロールから直接実行できないように維持する。
- 旧Cloudライブラリとログイン済みセッションの互換性を保つ。

## 本番リリース前の必須チェック

1. Supabaseプロジェクトの利用規約・プランを確認し、実際に復元できるDBバックアップ/復旧手順を確保する。バックアップ不能なら本番変更を停止する。
2. `supabase/functions/lyrictube-api/index.ts` の `LYRICTUBE_SIGNUP_KEY_SHA256` は**必須のサーバー環境変数**。本番関数に現在存在する作成キーのSHA-256を安全にSecretsへ移す。値をGitHub・Issue・CIログ・チャットへ書かない。未設定の場合は登録機能が503で停止する。
3. Edge Functionの `verify_jwt=false` は既存独自セッションに必要。署名JWTを用いない独自認証が動くまで勝手に `true` に変えない。
4. PRの全CI、特に一時PostgreSQLでの72/73バイトおよび日本語の拒否テストが合格していることを確認する。
5. ライブラリ4MiB超/大量同期/失敗後リトライを含め、実際の利用規模に応じた保存回帰を確認する。4MiBを超える正規使用があれば上限調整と再テストを行う。
6. 検証環境で**実際の旧アカウント**が従来のパスワードでログインできることを確認する（パスワードをログに記録しない）。
7. 別アカウントの操作・管理者と通常ユーザーの境界・間違った現在パスワードでの変更/削除拒否・正しいパスワードでの変更・既存セッション失効・新規作成キー不一致の拒否をテストする。
8. CSP/共有オリジン分離は別設計課題。GitHub Pages互換を維持する前提で、サイト移転を無断実施しない。

## 推奨する反映順序（本番デプロイは別作業）

1. Secrets設定とバックアップを確認し、先にフロントエンドをデプロイ（旧Edge Functionは追加したcurrentPasswordフィールドを無視できる）。
2. 新規パスワードのDB検証SQLを適用し、DB権限・既存ログイン・通常作成を読み取りで検証する。
3. Edge Functionをデプロイする。独自セッション認証の仕様として `verify_jwt=false` を明示する。
4. PC/スマートフォンでログイン・登録・管理者作成・パスワード変更・削除・保存・同期・ログアウトを通し、実測を記録する。
5. 403/401/413/500率とDB保存状態を観測し、失敗があれば古いEdge Functionにロールバックする。DB関数はバックアップ済みの元定義から必要に応じて復旧する。

**注意**：デプロイ済みEdge FunctionとGitHub上の新ソースはまだ同期されていない。GitHubコードだけ修正しても本番の認証は保護されない。Cloudflare/Supabase/GitHubアカウントを跨ぐ権限設定も別途確認する。

## 追加で解決すべき設計項目

- GitHub Pagesの共通 `elitemay.github.io` オリジンから、認証を扱うLyricTubeを専用ホストへ分離。ユーザーがホストとURL移行を承認してから実施する。
- トークンをJavaScriptの `sessionStorage` に保持する方式はXSS時の窃取可能性がある。独立ホスト＋HttpOnly Cookieや既存認証プロバイダーへの移行は、既存ユーザーのデータ移行設計と合わせて検討する。
- 30日セッションの継続期間と全端末ログアウトを再設計し、操作性と事故時の無効化を両立する。
